## 21:20 多级域名 / 内网地址的色键归一

## 22:00 Favicon 主色提取 —— 彻底解决分组色重复

**原问题**：`stringToAccent` 基于 10 色循环哈希，域名超过 10 个必然撞色，顶部色条视觉上无法区分站点。

**方案**：从 favicon 像素提主色，站点数 → 色相 1:1 不重复。

**新增文件**：
- `src/shared/utils/favicon-color.ts` —— Canvas 采样 + 4-bit 量化众数算法
  - 过滤透明/近白/近黑/灰像素
  - HSL 调色：亮度收敛 [0.42, 0.55]，饱和度 ≥ 0.55，保证色条显眼
  - 全局 Map 缓存 + in-flight Promise 去重，同一 favicon 只算一次

- `src/shared/hooks/useAccent.ts` —— React 适配层
  - 已缓存 → 同步返回；未算过 → 首帧用 `stringToAccent(colorKey)` 哈希兜底，算完切过去

**集成点**：
- `DomainGroupCard`：`useAccent(favicon, colorKey)` 替代原 `stringToAccent(colorKey)`
- `GridView.GridCard`：`accent.bar` 替代原 `stringToColor(colorKey)`，hex 色串天然支持 `${color}18` 拼 hex-alpha 渐变

- `<img crossOrigin="anonymous">` + canvas 读像素：Chrome 扩展里 favicon 多为同源（`_favicon/?...`），外链会被 CORS 挡住 → try/catch `getImageData` 吞异常，回退哈希色

## 22:12 关键 Bug：dev-mock 不响应写操作

**症状**：用户在浏览器预览下点关闭标签、一键合并重复、关闭域名组等按钮 → UI 不动 → 刷新页面才生效。

**根因**：`src/pages/newtab/dev-mock.js` 的 `chrome.tabs.remove/update` 是 `() => Promise.resolve()`，并且 `mockTabs` 数组也是不可变的——操作"成功"返回但数据没变，事件监听器全是 noop，`BroadcastChannel('canopy-sw-broadcast')` 也没人喊话，于是前端 `useSwBroadcast` 收不到 `tab-removed`，store 不会增量更新，只有 F5 后 `loadAllTabs` 重拉才看到结果。

**修法**：重写 dev-mock.js 让它成为**有状态的 mock**：
1. `mockTabs` 改 `let`，真正可变
2. `remove/update/create/move` 真实改数据 + dispatch 对应 `chrome.tabs.onXxx` 监听器 + 通过 `BroadcastChannel` 推送 SW 风格消息（tab-removed / tab-updated / tab-activated / tab-created / tab-moved）
3. **猴子补丁 `BroadcastChannel`**：规范下 postMessage 不会回投到自己所在 window，为了让 mock 和前端 `useSwBroadcast` 在同一个预览页内联通，在同 name 的实例间加了内存旁路投递
4. `windows.getCurrent` 补齐、`WINDOW_ID_NONE/CURRENT` 常量补齐（原版缺）

**验证点**：浏览器预览下点 DedupInfoBar 的"一键合并"、TabItem 的关闭按钮、DomainGroupCard 的关闭整组，UI 立即更新，无需刷新。

## 22:35 settings 切换"没反应"要刷新才生效 — 乐观更新

**症状**：用户反映 HeroBar 的视图切换 Segmented（域名分组/时间轴/紧凑列表/网格/使用频率）以及 SettingsPanel 里改任何项，都**点了没立即反应，刷新页面才生效**。

**根因**：`useSettingsStore.updateSettings` 旧实现是：
```ts
updateSettings: async (partial) => {
  const merged = await saveSettings(partial);  // ← 先 await 落盘
  set({ settings: merged });                    // ← 再 set
}
```
而 `saveSettings` 内部要 **2 次 chrome.storage 异步往返**（先 get 再 set），合计有几十到上百毫秒的延迟，用户感知就是"点了没反应"。尤其在 chrome.storage 写回慢或出错时，`set` 永远不会被调用，UI 彻底冻结直到刷新。

**修复**（`src/store/settings-slice.ts`）改为**乐观更新**：
1. 先同步 `set((s) => ({ settings: { ...s.settings, ...partial } }))` — UI 立刻刷新
2. 再后台 `try { await saveSettings(partial) } catch { console.error }`
3. 不回滚失败（下次刷新以 storage 为准，避免 UI 抖动）

**教训**：zustand 的 async action 如果要同时做"跨端持久化 + 本地 UI 反馈"，默认就应该**同步 set + 异步落盘**；先 await 再 set 只适合"必须成功后才承认"的场景（登录、支付）。设置项这种"怎么样都 OK"的东西绝不能 block UI。

## 22:45 antd Tooltip「首次正常，第二次不显示」bug

**症状**：Header/TabItem 里所有 `Tooltip` hover 首次能弹出，移开再 hover 就不出现了；或者出现明显延迟后才出。

**根因**：`src/shared/ui/AntdThemeProvider.tsx` 的 `themeConfig.components.Tooltip` 曾经这么写过：
```ts
Tooltip: {
  colorBgSpotlight: '...',
  colorTextLightSolid: '...',  // ← 这玩意是全局 Seed token，不是 Tooltip 的
  borderRadius: 8,
  boxShadowSecondary: '...',
}
```
- `colorTextLightSolid` 放在 `components.Tooltip` 里 **antd 不认**，导致文字色计算链断；

## 23:00 合并去重点了只转圈没效果

**问题（用户原话）**：
> 点击了合并标签只转圈没效果啊

**根因（两个叠加的 bug）**：
1. **全局 loading 滥用**：`tabs-slice.loadAllTabs` 会 `set({ loading: true })`，而 `App.tsx` 里 `{loading ? <Spin/> : <主视图>}`——也就是说 **任何调用 `loadAllTabs` 的地方都会把整个主视图盖成一个全屏 Spin**。`DedupInfoBar` 合并完成后 await `loadAllTabs()`，用户感知：
   - 「一键合并」按钮还在 loading
   - 主视图变成一大片转圈
   - 重复标签已被关掉 → `dupGroups` 为空 → Alert 自己 return null 卸载 → 只剩一个全屏 Spin
   - 视觉上 100% 等价于「点了只转圈没效果」
   同 bug 还潜伏在 `ArchivePanel.handleArchiveCurrent`（归档后刷新）和 SW broadcast 的 `tab-created` / `tab-moved`（每次新开/移动 tab 都会闪一次 Spin）。
2. **closeMultipleTabs 吞异常不重抛**：`chrome.tabs.remove` 失败时 `set({ error })` 后就算了，上层 `runClose` 看不到错误，仍会走到 `message.success`——假装成功。

**修复**：
- `loadAllTabs` 加 `options?.silent` 参数：silent=true 时只重置 error，不翻 loading；主视图不再被遮。
- `closeMultipleTabs` 的 catch 里除了 `set({ error })`，再 `throw err`，让调用方能感知。
- `DedupInfoBar.runClose`、`ArchivePanel.handleArchiveCurrent`、broadcast 的 `tab-created` / `tab-moved` 全部改走 `loadAllTabs({ silent: true })`。
- 首次初始化 `init()` 里仍用默认非 silent，保留 Spin 欢迎态。

**通用教训**：
- **全局 loading 只能用在「真·首次加载」**。任何「用户操作后的兜底刷新」都必须静默——否则主视图会被闪成 Spin，用户以为卡死了。
- Chrome Extension 里 SW broadcast 驱动的 refresh（tab-created 等）天然属于「静默刷新」场景，一定要和「用户点刷新按钮」这类显式场景在 loading 语义上分离。
- Zustand action 的 catch 里只 `set({ error })` 不重抛 = 吞错。调用方的 try/catch 永远走不到 catch，Promise 永远 resolve 成功——这是 React 代码里非常隐蔽的 silent failure 源头。日后新增 async action 要么重抛，要么明确文档化「本函数不会 reject，失败看 store.error」。

## 22:40 关闭标签"一直转圈 + tab 没关"

**用户反馈**：点合并去重 / 关闭按钮后 loading 一直转，浏览器 tab 根本没被关。

**根因**：`closeSingleTab` / `closeMultipleTabs` / `closeDomainGroup` / `closeAllNonPinned` 全都是 **先 `await addRecord(...)` 再 `await closeTab(s)(...)`** 的串行结构。而 `addRecord` 内部 `await setData(UNDO_STORAGE_KEY, records)` 又真的 await chrome.storage.local.set——任何一个环节（storage 容量超限、SW 状态异常、I/O hang）Promise 不 resolve，后面的 `chrome.tabs.remove` 就永远不会执行，且外层调用方（DedupInfoBar）的 `busy=true` 永远没机会被 finally 清掉。

**修复（分两层防御）**：
1. **undo-slice.addRecord**：把 `await setData` 改成 `void setData(...).catch(...)` fire-and-forget。in-memory records 同步更新即可保证撤销功能可用，持久化失败只打 console.warn 不阻塞调用方。
2. **tabs-slice 四个 close action**：给 `addRecord` 外再包一层 `.catch` 兜底（双保险），并且 `closeSingleTab` 也改为 `throw err`（和 `closeMultipleTabs` 对齐），让未来任何 UI 层的 try/finally 都能正常清 loading。

**通用教训**：
- **"锦上添花"功能（undo、analytics、metrics）绝不能被 await 在主业务路径上**——持久化失败/延迟会把主流程拖死。要么 fire-and-forget，要么超时兜底。
- Zustand store 里的 async action 如果 catch 里只 `set({ error })`（吞错），会让所有加了 `loading` 的调用方卡死——必须 `throw` 或者在文档里极明确说明"本函数永不 reject"。

**文件**：`src/store/undo-slice.ts`（addRecord 改 fire-and-forget）、`src/store/tabs-slice.ts`（四个 close action 统一加 catch + throw）

## 封板后补丁：消除 favicon 跨域控制台报错

**背景**：封板后用户反映控制台仍有跨域报错（favicon 引起）。之前多轮对话中遗漏了这个问题，本次收尾一起解决。

**三个源头 & 修复**：

1. **`getFaviconUrl` 用错 URL**：原实现是 `chrome://favicon2/${size}/${origin}`。这在 MV3 里**不合法**——MV3 的正确入口必须是 `chrome-extension://<chrome.runtime.id>/_favicon/?pageUrl=...&size=...`（manifest 里要声明 `favicon` permission，我们已声明）。访问 `chrome://favicon2/` 会被浏览器拒绝并打红控制台。
   - 改成读 `chrome.runtime.id` 动态拼 `_favicon/` URL
   - 无扩展上下文（本地 `pnpm dev`）返回空串，让调用方兜底

2. **`<img src={tab.favIconUrl}>` 直接用远程图标**：Chrome 给的 `tab.favIconUrl` 经常是站点原图 URL（如 `https://www.google.com/favicon.ico`），站点离线 / 不允许跨域 / 图标 404 时 `<img>` 会在控制台打 `net::ERR_*` 红字（即使有 `onError` 兜底，浏览器级报错 JS 抓不住）。
   - 在 `tabToLiveTab` / broadcast `tab-updated` 分支 / archive-service 归档三处**统一改写**成扩展同源的 `_favicon/` 入口
   - 同源 URL：Chrome 内部自己去抓远程图标（失败静默返回空图），绝不污染控制台
   - 恢复后所有 `<img>` 渲染 favicon 都走同源，不再有跨域告警

3. **`favicon-color.ts` 取色时用 `crossOrigin="anonymous"`**：即使对方拒绝 CORS 只会触发 `onerror`，但浏览器仍会在控制台打一条 CORS 红字。
   - 新增 `isSameOriginUrl()`，只有与页面同源（扩展 `_favicon/` / `data:` / `blob:`）才尝试取色
   - 同源图片**不再设置 `crossOrigin`**，避免多余预检
   - 跨源直接 `resolve(null)`，由 `stringToAccent` 哈希兜底（视觉上可能撞色，但控制台彻底干净）

**结果**：tsc ✓ / build 423ms ✓ / lint 0 error 3 warning（老三条规则局限）。控制台彻底静默。

**教训**：Chrome MV3 的 `_favicon/` API 是唯一合法的 favicon 入口，manifest 要声明 `favicon` permission + URL 用 `chrome-extension://<id>/_favicon/?pageUrl=...&size=...`；**禁用** `chrome://favicon2/`。对所有来自 chrome API 的 URL（tab.favIconUrl、归档快照），进入 store / 存储前就要做同源化替换，不要等到 `<img>` 出错。

  但在 4px 细色条 + 白底的物理约束下，克制路线的对比度永远不够
- 鲜艳色带来的"活力感"反而成为产品特色（多标签页管理器的"情绪价值"）
- 如果后续要退回克制版，只需把 `buildAccentFromHue` 的 3 个参数元组改回去即可

## 色条宽度 & 撞色二次修复

**用户反馈**：截图中色条太宽，19 组里 GitHub / tapd / tcloud4api / edgeone.cloud / 127.0.0.1 等多张卡都是"一模一样的红色"。

**根因**：
1. **色条太宽**：4px（hover 5px）把 favicon 和标题的视觉权重都抢了
2. **系统性撞色**：19 组 > 12 色相池 + MIN_SEPARATION=35° → `findFarthestHue` 在 N > 10 后会反复返回"当前圆上最松的同一个点"，造成后段所有卡都落在相同 hue

**改动**：

1. **色条收窄**（`DomainGroupCard.tsx`）：4→2（hover 5→3），left / top 两种位置同步
   - 2px 保留"身份索引"语义，不再喧宾夺主
   - hover 3px 仍有轻微反馈感

2. **`findFarthestHue` 引入 seed 抖动**（`useGroupAccents.ts`）：
   - 原实现：一遍扫描 0-359 返回"最大最小距离"的第一个 hue → 多卡撞同一点
   - 新实现：
     a. 先扫出"最大最小距离"
     b. 收集所有达到该距离的候选 hue（通常是等距多个点）
     c. 用 colorKey 哈希的 `hashDeg` 稳定从候选中挑位置
   - 效果：同一 colorKey 永远稳定分到同一位置，但不同 colorKey 分到**等距候选中的不同点**，打破系统性撞色

3. **`hashDeg` 辅助**：把字符串哈希到 0-359，既给首色选择用，也给 findFarthestHue 的 seed 用

**校验**：tsc 0 错 / build 594ms / lint 0 错。

**预期效果**：
- 色条从显眼粗条变成克制细线（2px 左竖线，像是 VSCode 侧边栏 dirty 标记）
- 超出 12 色相池的分组会分到"等距候选"的差异化位置，不再所有人挤在同一 hue

## 色彩系统三次迭代 —— 水彩版封板

**用户反馈**：多巴胺版（S=0.85）色条跟 antd 极简白底风格完全撕裂，"太刺眼了，跟主题不匹配"。同时很多颜色还是相同。

**根因**（三次迭代的教训）：
1. **克制版 S=0.42**：白底对比度不足，用户说"看不清、容易冲突"
2. **多巴胺版 S=0.85**：跟 antd 文档式极简风格撕裂，用户说"太刺眼"
3. **水彩版 S=0.48 / L=0.68**：柔和但可辨，与 antd 调性协调

**核心洞察**：色彩参数必须服从 **UI 整体调性**——antd 的"白底+细灰线+小圆角"文档风不吃"多巴胺"，高饱和在这种环境下像"贴了荧光便签"。

**关键改动**：

1. **水彩参数**（`favicon-color.ts` buildAccentFromHue）：
   - barLight: S=0.48, L=0.68（原 0.85 / 0.58）
   - barDark: S=0.55, L=0.62（原 0.80 / 0.66）
   - soft: barLight + 18% 透明（原 14%，让 favicon 徽章底色更可感）
   - 新增 **lShift 入参**：同色相下的明度微抖动（-0.06 ~ +0.06）

2. **色相池扩容**（`color.ts`）：12 → **20 色**
   - 平均间隔从 30° 降到 18°
   - 剔除土黄（45°-55°）和黄绿（85°-95°）两段
   - 理论最大支撑 20 种无冲突身份色

3. **批次去重优化**（`useGroupAccents.ts`）：
   - MIN_SEPARATION: 35° → **20°**（匹配新色相池间隔）
   - 新增 **hueCount 计数** + **occurrence 摆动**：
     - 同 hue 第 1 次出现 → L 不变
     - 第 2 次 → L+5%
     - 第 3 次 → L-5%
     - 第 4 次 → L+10%（裁剪到 ±6%）
     - 第 5 次 → L-10%
   - 效果：同色相的多张卡在亮度维度上拉开差距，肉眼可分

**校验**：tsc 0 错 / build 620ms / lint 0 错。

**预期观感**：
- 色条从"荧光霓虹"变"水彩粉笔"，跟白底极简 UI 和谐共生
- 19 组里相邻卡不再大面积撞色：首选 20 色池均分 → 超出后 L 抖动兜底
- favicon 徽章底色（soft）稍浓，色彩信息点集中在图标周围而非色条
