# GroveTab UX 设计文档

- **文档日期**：2026-05-21
- **适用对象**：`GroveTab / 林栖标签页`
- **文档目标**：基于当前仓库真实实现状态，给出下一阶段可执行的 UX 重构方向
- **结论先行**：当前产品**确实缺少“常用站点 / 快捷站点 / Speed Dial”能力**，但更准确地说，缺少的是一个位于首页上半屏、承担“快速开始下一步”职责的**轻启动层**

---

## 一、结论摘要

当前 `GroveTab` 的主能力已经很清楚：它是一个以**标签整理、搜索、归档、恢复**为核心的本地工作台。它的问题不在于核心能力弱，而在于首页只强调了“整理”和“管理”，却没有给用户一个足够自然的“立刻开始”入口。

对于新标签页产品来说，用户每次打开页面通常只做三类事：

1. **打开一个常用网站，马上开始下一步**
2. **回到刚才的工作上下文**
3. **整理已经失控的标签状态**

当前产品把第 2、3 类做得不错，但第 1 类做得不够。于是首页会出现一种体验落差：

- 搜索很强，但它偏“主动检索”
- 工作台很强，但它偏“管理与恢复”
- 归档很强，但它偏“收纳与回看”
- **唯独“快速打开常用目标”这一层很弱**

因此，本次 UX 设计文档的核心判断是：

> `GroveTab` 下一阶段不应继续堆更多边缘能力，而应优先补齐首页“轻启动层”，其中最关键的模块就是 **常用站点**。

---

## 二、现状判断与证据

### 2.1 当前首页的真实结构

基于当前 `App.tsx` 的渲染链路，首页主路径是：

- `Header`
- `HeroBar`
- `OnboardingCard`
- `SelectionModeNotice`
- `TidySuggestionBar`
- 主视图区
- `SearchBox / SettingsPanel / InsightsPanel` 等抽屉或浮层

同时，Header 里还保留了三个并列一级空间：

- `workspace`
- `trending`
- `devtools`

这意味着当前首页承担了三种完全不同的任务：

- 工作台管理
- 热榜浏览
- 开发工具操作

### 2.2 当前没有发现“常用站点”现行挂载

本次复核中，能确认以下事实：

- 当前仓库中**没有可直接使用的 `SpeedDial` 组件文件**
- 当前首页主链路中**没有“常用站点”区域**
- 当前 `uiVisibility` 只包含：`header / heroLogo / heroTitle / heroSlogan / heroSearch / viewSwitcher / tidySuggestion`
- 也就是说，当前系统连一个“站点快捷模块”的显隐开关都没有

### 2.3 但历史文档与注释明确留下了遗迹

仓库里仍然保留了几条很关键的证据：

- `CHANGELOG.md` 提到过 `SpeedDialWidget`
- `storage-repo.ts` 的 schema 注释里写过“**网站快捷模块**”
- 旧 PRD 和旧分析文档中还保留了 `DashboardOverview`、`HeroWidgets`、`ActivityStrip` 等首页增强层的叙事

这说明问题不是“团队从未考虑过常用站点”，而更像是：

> 这个能力曾经进入过产品结构，但现在已经从当前主链路中消失，留下的是文档、样式、存储层和命名上的残影。

### 2.4 因此，问题不是“要不要加一个新功能”

更准确的说法是：

> 首页原本应该有一层承接“高频起步动作”的能力带，但目前这层缺失了。

而“常用站点”正是最合适、最符合新标签页场景的承接模块。

## 三、为什么 `GroveTab` 需要常用站点能力

### 3.1 新标签页不是纯管理页，它首先是起点页

即使 `GroveTab` 的核心是标签工作台，用户打开新标签页时，第一反应依旧常常不是“我要整理”，而是：

- 打开 GitHub
- 打开飞书 / 企业微信 / 腾讯文档
- 打开设计稿
- 打开某个固定工作系统
- 打开常看的资讯或工具

如果产品不能很好地支持这种高频轻动作，用户会自然退回浏览器默认书签栏、地址栏建议，或者另装一个 Speed Dial 类扩展。

这会带来两个问题：

- `GroveTab` 会失去“每次打开都值得看一眼”的资格
- 用户会把“启动入口”交给别的产品，而把 `GroveTab` 只当作“出问题时才来整理”的工具

### 3.2 它补的不是功能空白，而是体验闭环

当前产品强的是：

- **收纳**：归档
- **恢复**：会话找回
- **整理**：去重、闲置、批量操作
- **检索**：搜索、筛选、多视图

但缺了一块：

- **直达**：我现在就要去那个地方

一旦补上常用站点，首页体验会形成完整闭环：

- **直达开始**：常用站点
- **进入管理**：工作台概览 / 搜索
- **处理混乱**：整理建议
- **回顾历史**：归档 / 最近操作

### 3.3 它还能降低搜索的认知负担

当前 `SearchBox` 很强，但能力强就意味着理解成本高。不是所有高频动作都应该走搜索。

对于“我就是想打开固定 8 个网站之一”这类任务，最好的设计不是输入，不是弹层，不是命令中心，而是：

- 一眼能看到
- 一次点击即达
- 排序符合我的习惯

也就是说，常用站点能把一部分高频、低思考成本的动作，从搜索系统里分流出去。这样搜索反而会更聚焦在它更擅长的事上：

- 找已打开标签
- 找归档会话
- 找书签
- 找历史记录
- 调用动作命令

### 3.4 它与“本地优先”并不冲突

常用站点能力完全可以保持本地优先：

- 手动添加的站点保存在本地
- 排序和分组保存在本地
- 若要做智能推荐，也可以基于本地书签、历史、固定标签、最近访问频率计算
- 无需云同步、无需外部推荐服务、无需内容画像

因此，它是一个**非常符合当前产品理念**的增强方向。

## 四、下一阶段产品策略

### 4.1 明确首页主叙事

建议把产品叙事明确为：

> `GroveTab` 是一个本地优先的标签页工作台，同时提供快速启动、上下文恢复和标签整理能力。

这里有一个关键变化：

- 过去的叙事重心偏“管理”
- 下一阶段的叙事应升级为“**启动 + 管理 + 恢复**”

### 4.2 首页只服务一个主场景

首页必须围绕一个问题展开：

> **“我现在下一步要去哪里，或者要如何回到工作状态？”**

所以首页上半屏必须优先承载：

1. 快速启动
2. 快速恢复
3. 快速整理

而不是先把不同性质的一级空间并列出来。

### 4.3 产品分层建议

建议把产品分成三层：

| 层级 | 角色 | 包含能力 |
| --- | --- | --- |
| **主层** | 工作台主体验 | 搜索、常用站点、工作区、整理建议、主视图、归档 |
| **辅层** | 附加空间 | 热榜、开发工具栏 |
| **深层** | 专业设置与数据控制 | 设置、数据管理、洞察、权限、危险区 |

核心原则是：

- **主层高频、明确、默认可见**
- **辅层存在，但不抢主层注意力**
- **深层强大，但不压在默认体验前面**

## 五、首页信息架构重构方案

## 5.1 建议的新结构

建议把 `workspace` 首页调整为如下结构：

```text
Header（精简）
Hero Search（保留）
Quick Start Layer（新增）
  ├─ 常用站点
  ├─ 最近工作区 / 最近归档 / 继续上次工作
Workspace Summary（轻量概览，替代沉重 Dashboard）
Tidy Suggestion（保留）
Main Views（现有多视图）
Secondary Entry（弱化后的 热榜 / 开发工具栏）
```

### 5.2 各层职责

#### A. Header：只做全局壳，不做主内容承载

Header 建议保留：

- 品牌标识
- 搜索唤起入口
- 主题切换
- 设置入口
- 洞察入口

建议弱化：

- `workspace / trending / devtools` 这种强并列一级切换

建议替代为：

- 一个“更多空间”入口
- 或在右上角用较轻的二级菜单承载

原因很简单：Header 不是产品价值说明书，它是全局工具条。

#### B. Hero Search：继续保留，但语义更聚焦

Hero 区应继续保留大搜索框，因为它是当前产品最具识别度的核心入口之一。

但它的定位要更清楚：

- 不是“替代常用站点”
- 不是“承载一切动作”
- 而是“全局检索与命令中心”

#### C. Quick Start Layer：新增首页轻启动层

这是本次重构的关键。

建议包含两个模块：

1. **常用站点**（主模块）
2. **继续工作**（辅模块）

其中：

- 常用站点负责“去目的地”
- 继续工作负责“回上下文”

#### D. Workspace Summary：保留概览，但不做大而全卡片墙

当前产品如果要恢复 `DashboardOverview` 思路，也不建议做成信息过满的大统计面板。

更推荐做成轻量摘要条，展示：

- 当前标签数
- 重复/闲置提醒
- 最近归档入口
- 一键整理

它应该是“工作状态摘要”，而不是“第二个首页”。

#### E. Main Views：继续承载深度管理

域名、时间轴、紧凑、网格、窗口、书签、归档、看板这些视图仍然是产品核心资产，不需要推翻。

问题不是这些视图太多，而是它们目前直接暴露在主入口的前排，缺少一个更轻的上层缓冲。

## 六、“常用站点”模块详细设计

## 6.1 模块定位

模块名称建议使用以下其一：

- **常用站点**（最直接，中文理解成本最低）
- **快捷站点**（更强调动作）
- **常用入口**（更宽泛）

不建议直接对用户使用 `Speed Dial` 作为主文案。它更适合作为设计/研发内部术语。

### 6.2 核心目标

这个模块只做一件事：

> 让用户在 1 秒内打开自己最常去的目标网站。

因此它必须满足：

- 快速可见
- 一击直达
- 排序可控
- 编辑简单
- 不依赖复杂权限

### 6.3 MVP 范围

建议 MVP 先做以下能力：

| 能力 | 建议 |
| --- | --- |
| 新增站点 | 手动添加 URL + 自动读取标题/favicon |
| 编辑站点 | 改标题、改 URL、自定义图标颜色或 emoji |
| 删除站点 | 支持删除，提供短暂撤销 |
| 排序 | 拖拽排序 |
| 打开方式 | 当前标签打开 / 新标签打开 |
| 数量 | 默认 8 个，最多 12 个 |
| 布局 | 2 行网格，宽屏可扩到 3 行 |
| 空状态 | 一键从当前标签添加 / 从书签推荐添加 |

MVP **不要一开始就做太多复杂能力**，例如：

- 多文件夹
- 云同步
- 复杂统计推荐
- 自动分类
- 大量主题化样式

这些都可以后续迭代。

### 6.4 推荐的数据来源优先级

建议采用双轨：

#### 轨道 1：显式收藏

这是主轨道。用户自己决定哪些站点出现在首页。

来源可以包括：

- 手动添加链接
- 从当前标签“加入常用站点”
- 从书签一键加入

#### 轨道 2：本地智能建议

这是辅轨道，只在空状态或编辑态提供建议，不直接替代用户控制。

建议来源：

- 最近高频访问域名
- 已固定标签所属域名
- 书签栏常见域名
- 最近归档会话中高频站点

关键原则：

- **建议不是自动替用户上屏**
- **建议必须是可选、可拒绝、可关闭**
- **若依赖历史/书签权限，要在对应时机再申请**

### 6.5 视觉形式建议

#### 方案建议：卡片式图标网格

每个站点卡片包含：

- favicon 或首字母图标
- 站点标题
- 域名副标题
- hover 时出现快捷操作

视觉风格建议：

- 与当前毛玻璃卡片体系一致
- 尺寸比主视图卡片轻
- 支持大圆角
- 支持按皮肤走统一 token
- 暗色模式下优先确保辨识度，不追求过度装饰

#### 卡片状态

- 默认：静态可点击
- hover：轻微上浮 + 显示编辑/移除按钮
- focus：明确键盘焦点环
- drag：卡片半透明 + 占位高亮
- loading：首次抓取 favicon/title 时显示骨架
- error：域名无效或 favicon 抓取失败时降级为首字母图标

### 6.6 推荐布局

#### 桌面默认布局

- 第一行 4 个
- 第二行 4 个
- 共 8 个

在超宽屏可扩展为：

- 单行 6 个，双行 12 个

但默认不建议一次性铺太多。原因是：

- 首页上半屏还要给搜索与工作区摘要留空间
- 太多会重新制造视觉拥堵
- 用户真正高频的固定目标通常不会很多

### 6.7 推荐交互

#### 单击

- 在当前标签页打开，适合“起步动作”

#### `Cmd/Ctrl + Enter` 或卡片菜单

- 在新标签打开

#### 右上角“+”

- 添加站点

#### 卡片 hover 菜单

- 编辑
- 删除
- 在新标签打开
- 从当前标签替换

#### 拖拽排序

- 只在编辑态或 hover 时出现拖拽句柄
- 避免正常点击与拖拽冲突

### 6.8 空状态设计

空状态必须让用户 10 秒内完成第一次配置。

建议文案：

- 标题：`把你最常去的站点放在这里`
- 说明：`每次打开新标签页，一键直达你的工作入口`

建议按钮：

- `添加当前标签`
- `手动添加站点`
- `从书签推荐导入`

空状态不应只有一段说明文字。它需要直接推动首个成功动作。

## 七、首页“继续工作”模块设计

如果只加常用站点，还不够完整。因为 `GroveTab` 的真正优势不是打开网站，而是恢复上下文。

因此建议在常用站点旁或其下方增加一个轻量模块：**继续工作**。

### 7.1 模块目标

帮助用户从“打开新标签页”快速回到：

- 最近工作区
- 最近归档会话
- 最近访问视图
- 最近操作结果

### 7.2 展示优先级

建议最多只展示 2–3 个项目，例如：

- 最近归档：`产品评审资料 · 28 tabs`
- 最近工作区：`EdgeOne 发布`
- 继续上次视图：`归档 / 看板 / 域名分组`

它应该是短、轻、立即可点的摘要，而不是另一套内容流。

### 7.3 与常用站点的关系

- **常用站点**：去一个目标页面
- **继续工作**：回一个工作上下文

两者放在一起，首页就具备了“去目的地”和“回上下文”两种核心能力。

---

## 八、对现有模块的取舍建议

## 8.1 `trending` 的位置调整

建议把 `TrendingPage` 从并列一级入口降为：

- Header 里的轻入口
- 或“更多空间”里的子入口
- 或用户主动开启的附加页签

原因：

- 它不是工作台主任务
- 它依赖外部接口
- 它会稀释本地优先叙事

### 8.2 `devtools` 的位置调整

建议把开发工具栏也从首页一级并列入口下沉。

原因不是它不重要，而是：

- 它的目标用户更窄
- 它的任务模型和工作台不同
- 它应该像“附加工具箱”，不是每次打开新标签页都抢注意力的主空间

### 8.3 `DashboardOverview` 的重建策略

如果团队后续要恢复这个模块，建议不要完全照着旧 PRD 的“大概览卡片群”回归。

更推荐：

- 做成轻摘要
- 只保留最关键的状态与动作
- 不和常用站点抢首屏重心

可以把它理解为：

- 常用站点负责“开始”
- 概览条负责“状态提醒”

### 8.4 `ActivityStrip` 的重建策略

`ActivityStrip` 不是不能做，而是优先级要后于常用站点。

因为：

- 最近操作是“回顾”
- 常用站点是“启动”

启动层缺失时，先做活动流会让首页继续偏向“系统状态面板”，而不是“高频工作入口”。

## 九、设置系统重组建议

当前设置面板的问题不是功能少，而是语言太像控制台。

建议从“技术属性分组”改为“任务分组”。

### 9.1 建议的新分组

| 新分组 | 用户心智 | 典型内容 |
| --- | --- | --- |
| **首页布局** | 我想控制首页显示什么 | 常用站点、概览、整理建议、视图切换显隐 |
| **外观风格** | 我想更好看 | 主题、皮肤、背景、动效 |
| **搜索与效率** | 我想更快找到东西 | 搜索引擎、历史建议、热词、快捷键 |
| **数据与恢复** | 我想备份、迁移、重置 | 导入导出、清理、恢复默认、恢复出厂 |
| **高级选项** | 我知道自己在做什么 | Token 定制、视频背景、实验特性 |

### 9.2 “常用站点”相关设置建议

只保留必要项：

- 显示/隐藏常用站点
- 每行显示数量
- 显示标题或仅图标
- 是否显示智能建议
- 点击默认在当前标签 / 新标签打开

不要一开始就把所有高级配置都扔进设置里。

## 十、Onboarding 与引导改造建议

当前 onboarding 更像“工作台说明”，但下一阶段首页会同时承载：

- 快速启动
- 工作台管理
- 归档恢复

所以 onboarding 也要随之调整。

### 10.1 首次引导建议改成 4 步

1. **这是你的标签工作台**
2. **这里可以一键打开常用站点**
3. **这里可以搜索、整理、归档当前标签**
4. **这里可以随时回到上次工作上下文**

### 10.2 引导顺序原则

先讲轻动作，再讲深能力：

- 先让用户“会用”
- 再让用户“懂强大”

这比一上来讲复杂视图和设置更有效。

## 十一、关键交互流程

## 11.1 日常启动流

```text
打开新标签页
→ 看到搜索 + 常用站点 + 继续工作
→ 点击常用站点进入目标系统
```

目标：3 秒内完成。

## 11.2 恢复上下文流

```text
打开新标签页
→ 看到“继续工作”区域
→ 选择最近归档 / 最近工作区
→ 回到上次上下文
```

目标：降低“我刚才看到哪了”的认知成本。

## 11.3 整理流

```text
打开新标签页
→ 看见整理建议
→ 一键整理重复/闲置标签
→ 必要时进入主视图深度处理
```

目标：把管理动作放到第二层，而不是第一眼就压上来。

## 11.4 深度管理流

```text
打开新标签页
→ 通过视图切换进入域名 / 时间轴 / 看板 / 归档
→ 执行批量、归档、恢复、搜索等动作
```

目标：保留当前产品的深度优势，但不再让所有深能力都挤在首页第一屏前排。

## 十二、视觉与布局规范建议

### 12.1 首屏优先级

首页首屏视觉权重建议从高到低排序为：

1. Hero Search
2. 常用站点
3. 继续工作
4. 工作状态摘要
5. 整理建议
6. 主视图内容

这意味着：

- 搜索仍是品牌型核心入口
- 常用站点成为最高频动作区
- 工作台摘要退到辅助层
- 视图系统继续强，但从“首屏主角”变成“深度工作区”

### 12.2 视觉密度建议

常用站点区需要做到：

- 比主视图更轻
- 比书签栏更美观
- 比卡片列表更短

建议：

- 单卡高度偏小
- 图标与标题居中
- 二级信息弱化
- 保持呼吸感，不做重阴影堆叠

### 12.3 自适应建议

- 宽屏：常用站点与继续工作可并排
- 中屏：上下堆叠
- 窄屏：常用站点优先，继续工作折叠为摘要列表

## 十三、度量指标与验收标准

## 13.1 体验目标

引入常用站点后，首页应达成以下目标：

| 指标 | 目标 |
| --- | --- |
| 首次打开新标签后的首次有效点击时间 | 明显缩短 |
| 首页上半屏的点击集中度 | 提升 |
| 搜索框作为“打开常用网站”用途的占比 | 下降 |
| 工作台主链路使用后的回流率 | 提升 |
| 用户对首页复杂度的主观反馈 | 降低 |

### 13.2 功能验收标准

- 用户能在 30 秒内完成首个常用站点添加
- 用户能在 10 秒内理解“常用站点”和“工作台视图”的区别
- 用户不需要进入设置，也能理解首页主要可做什么
- 不依赖任何新外部服务即可完成 MVP
- 权限申请保持按需，不因为该模块扩大默认权限面

## 十五、最终建议

如果只回答用户最关心的那个问题，那么答案是：

> **是的，当前产品缺少“常用站点”能力。**

但从 UX 角度，更完整的结论是：

> **当前产品缺少的不是一个孤立功能，而是首页“轻启动层”。常用站点是这层里最关键、最符合新标签页场景、也最适合当前产品理念的模块。**

`GroveTab` 现在已经很擅长“整理过去”和“管理现在”，下一阶段最值得补上的，是“帮助用户立刻开始下一步”。

当首页同时具备：

- **常用站点**：快速出发
- **继续工作**：快速回到上下文
- **整理建议**：快速恢复秩序
- **多视图工作台**：深度管理

这个产品才会真正从“功能很多的标签扩展”，升级为“每次打开都值得使用的标签工作台”。
