# 03. 会话归档模块独立报告

模块范围：`sessions` + `services/archive`，覆盖一键归档、批量归档、归档列表、筛选搜索、合并、分享、重命名、恢复策略、自动快照和导入导出能力。

市场数据快照（Chrome Web Store，2026-05-25）：

| 产品                   | 用户量 | 评分 | 评论数 | 主要定位               |
| ---------------------- | ------ | ---- | ------ | ---------------------- |
| OneTab                 | 2M     | 4.45 | 14,527 | 一键收纳 / 省资源      |
| Session Buddy          | 1M     | 4.66 | 25,095 | 会话管理 / 恢复 / 备份 |
| Tab Manager by Workona | 200K   | 4.64 | 3,795  | 工作区与会话协同       |
| Tabs Outliner          | 100K   | 4.44 | 3,324  | 树状会话与任务流       |

结论：当前归档模块的“原子归档 + 局部恢复 + 批量管理”已经具备产品骨架，是 Canopy 最接近头部竞品的模块之一；但它仍偏向“静态快照仓库”，还不是“高保真会话系统”。如果不补强导出格式、并发安全、结构化恢复和大体量存储，这个模块很难真正击穿 OneTab 与 Session Buddy 的成熟用户心智。

## 1. 功能完善度评估

完成度评分：74/100。

- 核心链路完整：支持一键归档、按窗口或所选标签归档、会话列表、重命名、删除、合并、恢复到新窗口或当前窗口、会话级搜索和高亮。
- 数据路径合理：已经具备 `chrome.storage.local` 与 IndexedDB 降级思路，说明团队已意识到归档模块的容量和持久化边界。
- 批量操作意识较强：大批量恢复分批执行，Undo 也有对应设计，基础稳定性优于很多纯工具型扩展。
- 当前问题集中在“格式与规模”：虽然底层工具函数已支持多种导出格式和 OneTab 导入，但设置 UI 仍主要暴露 JSON，产品价值没有完全释放。
- 当前问题集中在“恢复保真”：归档保存了标签，但对窗口结构、组结构、焦点顺序和关键状态的保留还不够系统。
- 当前问题集中在“并发一致性”：归档、导入、恢复、清空等操作都涉及多源写入，目前缺少显式并发锁与任务队列治理。

## 2. 对标主流竞品的核心能力欠缺与短板

- 对标 OneTab，Canopy 的“省心程度”还不够极致。OneTab 的核心竞争力是极少决策成本，而 Canopy 虽然功能更强，但路径更长，导出与回收链路还没有完全收敛成一套顺手动作。
- 对标 Session Buddy，Canopy 缺少“大型会话仓库能力”。Session Buddy 在大体量会话、备份恢复、结构化浏览和长期积累上更强；Canopy 当前更适合日常收纳，而不是长期知识仓库。
- 对标 Workona，Canopy 的归档还没有与工作区强绑定。归档更像独立仓库，而不是工作区生命周期的一部分。
- 对标 Tabs Outliner，Canopy 缺少树状上下文与任务流表达。会话仍以列表和卡片形式展示，层级关系和演化历史不够强。

## 3. 具体可落地的优化方向与改进建议

| 优先级 | 优化方向                   | Chrome / Web API                                               | 具体落地方式                                                                                                            | 预期收益                                 |
| ------ | -------------------------- | -------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------- | ---------------------------------------- |
| P0     | 做大体量归档仓库与压缩备份 | OPFS, IndexedDB, `CompressionStream`, `File System Access API` | 归档正文与大型索引放 OPFS/IDB，设置页提供 `.json.gz` / `.md` / `.html` 导出，并支持目录级备份                           | 归档从“轻量功能”升级为“本地资产仓库”     |
| P0     | 引入归档操作锁与任务队列   | `Web Locks API`                                                | 对归档、恢复、导入、清空、自动快照加全局锁，避免多标签页同时操作时出现重复写入、部分恢复和状态错乱                      | 降低数据竞争和边缘错误率                 |
| P0     | 补强结构化恢复             | `chrome.sessions`, `chrome.tabGroups`                          | 归档时记录窗口边界、TabGroup 标题/颜色、固定状态和恢复顺序；恢复时优先按原结构重建                                      | 把“能恢复”升级为“恢复得像原来一样”       |
| P1     | 让自动快照真正产品化       | `chrome.alarms`, `chrome.storage.session`                      | 把自动快照暴露为显式策略：最小 Tab 数、时间间隔、保留数量、工作时间例外；短期状态写 `storage.session`，最终结果落持久层 | 形成与 OneTab 不同的“智能静默备份”差异化 |
| P1     | 归档搜索升级为主搜索子域   | `chrome.offscreen`, OPFS                                       | 后台增量构建归档索引，并把会话结果回注到主搜索框；支持按会话名、标签、备注、域名和 OG 描述查找                          | 让归档从“仓库”变成“可搜索的第二记忆层”   |
