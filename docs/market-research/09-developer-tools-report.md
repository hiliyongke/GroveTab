# 09. 开发工具栏模块独立报告

模块范围：`developer-tools` + `local-tools.ts`，当前包含 30 个本地工具、9 个工具分类，覆盖 JSON/编码/时间/网络/前后端等基础开发工具。

市场数据快照（Chrome Web Store，2026-05-25）：

| 产品           | 用户量 | 评分 | 评论数 | 主要定位              |
| -------------- | ------ | ---- | ------ | --------------------- |
| JSON Formatter | 2M     | 4.28 | 2,082  | JSON 格式化 / 可视化  |
| Web Developer  | 1M     | 4.46 | 2,831  | 前端调试工具集        |
| ModHeader      | 900K   | 2.99 | 1,178  | 请求头修改 / 网络调试 |
| Octotree       | 200K   | 4.86 | 1,137  | GitHub 开发增强       |

结论：当前开发工具栏已经不是“附赠的小工具页”，30 个本地工具和多分类架构说明它具备独立产品雏形；但它仍是“静态转换工具集合”，还不是“真正和浏览器页面、网络请求、DevTools 工作流相连的开发工作台”。与 Web Developer、ModHeader、Octotree 相比，最大差距在上下文集成能力。

## 1. 功能完善度评估

完成度评分：64/100。

- 工具数量与覆盖面已经有一定厚度：当前 30 个工具覆盖数据、编码、网络、前端、后端、生成器等 9 个分类，能满足常见轻量开发需求。
- 工具体验较统一：搜索、收藏、右侧工作台、纯本地处理声明和单工具面板化设计，使模块具有较好的信息架构。
- 当前实现最大的优点是“零外发、低风险”。许多敏感输入，如 JWT、Base64、JSON 和随机串都能在本地完成处理，这一点优于很多在线工具站。
- 当前短板在“上下文缺失”：工具与当前页面、当前请求、当前 DOM、当前 Cookie、当前响应头之间没有关系，本质仍是孤立文本处理器。
- 当前短板在“可编排能力”不足：工具之间无法串联，缺少工作流、模板、批处理和片段沉淀。
- 当前短板在“性能与文件规模”上仍有潜在瓶颈：大 JSON、长文本 diff、复杂格式化仍运行在主线程，未来会碰到卡顿上限。

## 2. 对标主流竞品的核心能力欠缺与短板

- 对标 JSON Formatter，Canopy 的本地工具已覆盖基础格式化，但在大体量 JSON 浏览、树状折叠、路径定位和文件输入输出上仍偏轻。
- 对标 Web Developer，Canopy 缺少“页面上下文能力”。Web Developer 的强项不是字符串转换，而是直接作用于页面、表单、CSS、图片和布局。
- 对标 ModHeader，Canopy 没有请求级调试链路。当前网络类工具能“解析文本”，不能“作用于真实请求”。
- 对标 Octotree，Canopy 缺少场景专用增强。头部开发类扩展通常强绑定某一工作流，而 Canopy 当前更像通用工具箱，广而不深。

## 3. 具体可落地的优化方向与改进建议

| 优先级 | 优化方向                   | Chrome / Web API                                                                              | 具体可落地方案                                                                                                         | 预期收益                                     |
| ------ | -------------------------- | --------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------- | -------------------------------------------- |
| P0     | 增加真正的 DevTools 集成面 | `chrome.devtools.panels`, `chrome.devtools.inspectedWindow`, `chrome.devtools.network`        | 保留现有新标签页工具箱，同时新增 DevTools 面板版；让请求头分析、DOM 提取、Cookie 查看、JSON 美化直接作用于当前检查页面 | 从“工具页”升级为“开发者工作流工具”           |
| P0     | 打通文件与剪贴板工作流     | `File System Access API`, `navigator.clipboard.readText()`, `navigator.clipboard.writeText()` | 支持打开本地 JSON / HAR / 文本文件处理，处理后直接另存；支持一键从剪贴板导入和写回                                     | 明显提升日常使用频率，减少来回切换网页工具站 |
| P0     | 把重计算移出主线程         | Web Workers, `scheduler.postTask()`, `CompressionStream`                                      | 大 JSON 格式化、长文本 diff、批量编码转换放入 Worker；必要时对结果做压缩缓存                                           | 处理大文件时保持 UI 响应，提升专业感         |
| P1     | 增加当前页面上下文工具     | `chrome.scripting.executeScript`, `chrome.sidePanel`                                          | 对当前标签页注入只读采集脚本，获取 DOM、Meta、Cookies 可见摘要、选中文本和页面 URL，工具页直接消费这些上下文           | 补齐与 Web Developer / Octotree 的场景差距   |
| P1     | 建立片段与模板系统         | OPFS, `Web Locks API`                                                                         | 用户可保存常用正则、JSONPath、Header 模板、请求片段和输出模板；用锁保护并发写入                                        | 让工具从一次性使用升级为长期资产             |
