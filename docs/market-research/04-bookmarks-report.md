# 04. 书签中心模块独立报告

模块范围：`BookmarkView` + `bookmarks` 工具箱，覆盖书签树、列表/脑图/组织图视图、书签搜索、批量加入书签、去重、失效检测、智能整理和空文件夹清理。

市场数据快照（Chrome Web Store，2026-05-25）：

| 产品                      | 用户量 | 评分 | 评论数 | 主要定位                   |
| ------------------------- | ------ | ---- | ------ | -------------------------- |
| Raindrop.io               | 400K   | 4.12 | 776    | 收藏 / 书签同步 / 标签管理 |
| Toby: Tab Management Tool | 300K   | 4.21 | 3,279  | 集合式收藏与工作区         |
| Session Buddy             | 1M     | 4.66 | 25,095 | 会话与书签共管             |
| Tab Manager by Workona    | 200K   | 4.64 | 3,795  | 工作区与资源保存           |

结论：当前书签模块已经超出“调用 Chrome 书签 API 做展示”的基础水平，尤其是去重、失效检测和多布局展示，说明产品在书签治理上有明显野心；但它与 Raindrop、Toby 的差距依然存在，核心不在 UI，而在“规则化治理、实时同步和沉淀能力”。

## 1. 功能完善度评估

完成度评分：72/100。

- 基础展示较完整：支持权限按需申请、树状浏览、搜索、列表与图形化布局切换，已经具备“书签中心”而不是“书签页”的形态。
- 工具能力明显加分：重复书签扫描、失效检测、按域名聚类整理、空文件夹清理，说明模块已覆盖“发现问题”和“解决问题”两端。
- 当前实现偏“手动工具箱”，而不是“持续治理引擎”：大多数操作仍依赖用户主动打开书签页并触发，缺少后台监测、规则自动化和实时事件同步。
- 与书签规模增长相关的性能策略还不够明确：当前搜索和扫描可以应对中等规模书签，但超大收藏库下的索引构建和健康检测还缺稳定策略。
- 与项目其他资产联动不够：书签、归档、工作区和搜索仍然是多个相邻模块，而不是一套统一资源层。

## 2. 对标主流竞品的核心能力欠缺与短板

- 对标 Raindrop.io，Canopy 缺少“长期治理能力”。Raindrop 的强项是标签体系、规则化收藏、长期沉淀和跨设备一致性；Canopy 当前更像本地整理工具，而不是长期收藏系统。
- 对标 Toby，Canopy 缺少“收藏即工作区”的表达。当前书签更像浏览器资源库，而不是任务/项目的一部分。
- 对标 Session Buddy 与 Workona，Canopy 缺少“会话-书签双向转换链路”的顺滑体验。虽然已有“加入书签”等动作，但还没有形成批量规则、历史回流和项目级收藏语义。
- 当前失效检测与去重仍偏工具式：它们解决局部问题，但没有形成持续监控、例外规则、按目录治理和回溯视图。

## 3. 具体可落地的优化方向与改进建议

| 优先级 | 优化方向                 | Chrome / Web API                                                                         | 具体落地方式                                                                                                | 预期收益                                     |
| ------ | ------------------------ | ---------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------- | -------------------------------------------- |
| P0     | 建立书签实时同步层       | `chrome.bookmarks.onCreated`, `chrome.bookmarks.onChanged`, `chrome.bookmarks.onRemoved` | 监听书签事件，避免用户每次进入书签页才全量拉取；把增量更新同步到搜索索引和书签工具面板                      | 让书签中心从“静态页”变成“实时资源层”         |
| P0     | 把大扫描任务拆到后台     | `scheduler.postTask()`, Web Workers                                                      | 去重、健康检测、空文件夹扫描按分片执行；前台只收进度与结果                                                  | 大型书签库下不卡主线程，工具可持续扩展       |
| P0     | 给失效检测增加可复用缓存 | OPFS, `AbortSignal.timeout()`, `Web Locks API`, `Cache Storage`                          | 记录最近探测时间、HTTP 状态、错误类型和重试次数；对同一 URL 做短期缓存，防止反复探测                        | 降低网络压力与误报，提高治理效率             |
| P1     | 引入规则化整理           | `URLPattern`                                                                             | 支持 `*.figma.com/* -> 设计`、`*.github.com/* -> 开发` 等规则，把“智能整理”从按域名聚类升级为可配置规则引擎 | 更接近 Raindrop 的沉淀能力，但仍保持本地优先 |
| P1     | 开放文件级导入导出和修复 | `File System Access API`, `CompressionStream`                                            | 书签工具箱支持导出清洗后的 HTML/JSON、导入对账、生成重复/失效诊断文件                                       | 让书签模块具备“资产治理”和“数据迁移”能力     |
